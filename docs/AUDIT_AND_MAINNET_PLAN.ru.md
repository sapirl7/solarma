## 5. Путь к первому запуску

### Этап 1. Инцидент (§0)
Без этого этапа дальше идти нельзя: новые ключи на заражённой машине будут украдены так же.

### Этап 2. Код
1. Открыть PR из этой ветки, CI должен быть зелёным.
2. Решить P-1 (§6).
3. Внешний аудит контракта, параллельно с этапом 4.

### Этап 3. Новые ключи (чистая машина)
```bash
# Devnet и mainnet — РАЗНЫЕ ключи программы
solana-keygen new -o ~/solarma-keys/solarma_vault-devnet.json
solana-keygen new -o ~/solarma-keys/solarma_vault-mainnet.json   # можно vanity: solana-keygen grind
solana-keygen new -o ~/solarma-keys/deployer-mainnet.json        # горячий, только SOL на деплой
```
- Upgrade authority: Squads multisig (например, 2 из 3: Ledger, Seeker Seed Vault и ещё одно устройство).
- Treasury для Donate: новый адрес (vault в Squads или реальная благотворительность).
- Новый Android keystore, бэкап зашифрован, пароль в менеджере паролей.
- Seed-фразы на бумаге, в двух физически разных местах.

### Этап 4. Репетиция на devnet
```bash
cd programs/solarma_vault
# Cargo workspace лежит в programs/, поэтому anchor ищет keypair в programs/target/deploy/
# (проверь, куда его кладёт `anchor build`). Старый файл там — скомпрометированный F54Lp…
cp ~/solarma-keys/solarma_vault-devnet.json ../target/deploy/solarma_vault-keypair.json
anchor keys sync                 # declare_id! и Anchor.toml ← новый devnet ID
anchor build --verifiable
anchor deploy --provider.cluster devnet
```
Собрать APK с этим ID (`-PSOLARMA_PROGRAM_ID=<devnet id>`) и пройти `docs/QA_MATRIX.md` на
реальном Seeker. Отдельно проверить пробуждение, snooze, перезагрузку телефона и slash по каждому маршруту.

### Этап 5. Деплой в mainnet
Бюджет на deployer: около **5–6 SOL** (рента programdata около 2–3 SOL плюс временный buffer).
```bash
# declare_id! = mainnet ID (anchor keys sync с mainnet keypair), затем:
anchor build --verifiable
solana program deploy <путь к verifiable .so> -u <приватный RPC> \
  -k ~/solarma-keys/deployer-mainnet.json \
  --program-id ~/solarma-keys/solarma_vault-mainnet.json \
  --with-compute-unit-price 50000 --max-sign-attempts 50
solana program set-upgrade-authority <MAINNET_ID> \
  --new-upgrade-authority <SQUADS_VAULT> --skip-new-upgrade-authority-signer-check
solana program show <MAINNET_ID>          # authority = Squads
solana-verify verify-from-repo -u mainnet-beta --program-id <MAINNET_ID> \
  https://github.com/sapirl7/solarma --library-name solarma_vault --mount-path programs
```
Путь к `.so` бери из вывода `anchor build --verifiable`. Флаги CLI сверь со своей версией Agave.

### Этап 6. Релиз приложения
```bash
./gradlew assembleRelease -PSOLARMA_NETWORK=mainnet \
  -PSOLARMA_PROGRAM_ID=<MAINNET_ID> -PSOLARMA_TREASURY=<адрес> \
  -PSOLANA_RPC_MAINNET=<приватный RPC с ограничением ключа>
```
- Мягкий запуск: в UI ограничить депозит (например, до 0.1 SOL) до внешнего аудита.
- README: убрать «Currently on Devnet», указать mainnet Program ID и модель доверия (P-1).
- Публикация в dApp Store под новым ключом издателя, согласованная с Solana Mobile.

### Этап 7. После запуска
- Мониторинг событий программы (`scripts/monitor_program_events.cjs` или webhooks провайдера).
- Обновления контракта только через multisig, по `docs/UPGRADE_POLICY.md`.
- Снять лимит депозита после аудита и нескольких недель без инцидентов.

## 6. Решения, которые нужны от владельца

1. **Wake proof (P-1):** запуск на модели self-commitment или сначала PR #79.
2. **Donate:** реальная благотворительность или казна проекта. Во втором случае переименовать
   маршрут, чтобы не вводить пользователей в заблуждение.
3. **Приложение:** тот же `applicationId` с новым ключом (если Solana Mobile позволит перенос)
   или новый листинг.
4. **Upgrade authority:** состав Squads multisig.
